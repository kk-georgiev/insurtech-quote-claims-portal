## Findings

### Spec-to-implementation reconciliation — accept

- **FR-M3-11** (`app/roleHome.ts:getCurrentRole`) — reads `exp`, treats a stored-but-expired token as no session, everywhere the function is already called. No per-call-site change needed at `RoleGuard`/`RootLayout`.
- **FR-M3-12** (`api/sessionExpiry.ts`, `api/client.ts`, `app/browserRouter.ts`) — a 401 from an *authenticated* call clears the token and triggers a real navigation to `/login`, scoped correctly away from a wrong-password login 401.
- **FR-M3-13** (`app/GuestGuard.tsx`, `router.tsx`) — an authenticated visitor is redirected off `/login`/`/register` to their own role home; `/health` stays reachable either way.

All three traced to source and independently confirmed live against the real merged backend (see Behavior verification), not only against mocked tests.

### Deferred-backlog items closed — accept, worth recording explicitly

Two long-standing entries in `deferred-work.md` describe exactly the gap FR-M3-11 closes, and neither file is ever edited to reflect that (append-only, by its own header) — recording it here is the only place this closure becomes visible to a later reader:

- **Item 260** (Story 2.4): *"`getCurrentRole()` decodes the stored JWT and trusts its `role` claim without checking the `exp` claim, so `RoleGuard` treats an already-expired-but-decodable token as a valid session."* — closed by this epic's `exp` check.
- **Item 350** (Story 2.5): *"The auth-aware nav (and `RoleGuard`) treats any token with a well-formed `role` claim as 'logged in,' with no check against the token's own `exp` claim."* — same gap, closed the same way.

Both are two epics old — this is a case of a deferred item actually getting picked back up, not just accumulating.

### Deferred-backlog items correctly still open — not a gap in this epic

Checked against the same file, three related entries this epic's narrow scope was never going to close, and didn't:

- **Item 264**: `RoleGuard`'s redirect drops the originally-requested location (no `state={{ from: location }}`, no return-to-intended-page after login). Unrelated to FR-M3-11/12/13.
- **Items 272/346**: cross-tab reactivity — a token cleared or changed in another browser tab doesn't cause an already-mounted guarded route or the nav to react, since nothing subscribes to the `storage` event. Both entries explicitly note this is a pre-existing architectural gap no single wrapper component was going to close. Session-death handling this epic adds (Story 7.1's 401 path) is itself *within-tab* — it does not touch this gap either, since `notifySessionExpired()` only ever fires from that same tab's own failed request.

Neither omission is a defect; both are exactly what the epic's declared "narrow fixes" scope said it would leave alone.

### Duplication / architecture — accept, no new finding

`GuestGuard` and `RoleGuard` are structurally parallel (both read `getCurrentRole()`, both wrap `Outlet`/`Navigate`) but not duplicative — they gate on inverse conditions (any valid role vs. one specific role) and each is eight lines. Unifying them would trade a marginal line-count reduction for a harder-to-read conditional; correctly left as two small, single-purpose components, matching `RoleGuard`'s own established pattern.

The `api/sessionExpiry.ts` pub-sub — the one genuinely new architectural piece this epic adds — does what it was built for: `client.ts` never imports react-router or the route table, and the import graph stays acyclic (verified by construction and by `browserRouter.test.ts` actually importing the real module graph without error).

### God-class watch — not triggered

The highest-churn test files this epic (`router.test.tsx` +59, `LoginForm.test.tsx` +45, `roleHome.test.ts` +71 net lines) land at 181/343/111 lines respectively — none approaching the concern `QuoteControllerTest.java` raised in Epic 6's retro (644 lines). No action item.

### Cross-story boundary check — accept

The one place this epic's two stories interact — an authenticated call's 401 clears the token and navigates to `/login` (7.1) while `GuestGuard` (7.2) simultaneously governs who may render that same route — was traced for a race: `client.ts` calls `clearToken()` *before* `notifySessionExpired()`, synchronously, so by the time `GuestGuard` evaluates the resulting `/login` render, `getCurrentRole()` already reads the cleared token. No stale-role redirect loop is possible by construction. This is exactly the kind of interaction a single story's own review can't see and the retro exists to check — verified clean.

## Behavior verification

Exercised live against the real merged backend (`docker compose up --build`), for both stories:

**Story 7.1 (FR-M3-11/12):**
1. Seeded an expired-but-well-formed token, navigated to `/` — redirected straight to `/login`, confirmed via `window.location.pathname`.
2. Seeded a token the *client* accepts (valid `exp`, real role) but with a forged signature the *backend* rejects — navigated to `/quotes`, watched it load, then get a real 401, clear the token, and navigate to `/login` — the whole chain, no mocks.
3. A normal login still landed on the client shell exactly as before.

**Story 7.2 (FR-M3-13):**
4. While authenticated, navigated straight to `/login` — redirected to `/` without the form ever rendering.
5. Same for `/register`.
6. Cleared the session, confirmed `/login` reachable normally again for an anonymous visitor.

One gap in this verification, honestly noted rather than silently skipped: step 2 confirmed the *content* area showed the login screen and the token/path were correct, but did not separately re-screenshot the *header nav* (Register/Login visible, no Logout) at that exact moment — RootLayout reads the same `getCurrentRole()` the client-side-expiry case (step 1) already confirmed shows anonymous nav correctly, so this is mechanistically guaranteed rather than independently re-observed for the 401 path specifically. Not treated as an open item; noted for completeness.
