### Aggregate views — duplication / reuse

- **`PolicyController.currentUserId(Authentication)` duplicates `QuoteController.currentUserId(Authentication)` byte-for-byte** (`backend/src/main/java/com/motorinsurance/policy/api/PolicyController.java:57-59` vs. `backend/src/main/java/com/motorinsurance/quote/api/QuoteController.java:105-107`) — both cast `authentication.getPrincipal()` straight to `UUID`. Confirmed by direct read of both files. A third controller (agent/claims, later milestones) will likely copy this a third time rather than pull it from a shared place. This is a new copy of an already-known gap: `deferred-work.md`'s Story 1.6 entry already flags the missing-failure-handling half of this same helper (`ClassCastException` surfacing as a raw 500) as a pre-existing, accepted risk — this finding is about the *duplication*, not that pre-existing risk, and the duplication is new to this epic.

### Aggregate views — efficiency (minor, all confirmed by direct read)

- **`QuoteService.policyIdFor` routes a single-quote lookup through the batch method.** `backend/src/main/java/com/motorinsurance/quote/application/QuoteService.java:148-153` calls `policyService.findPolicyIdsByQuoteIds(customerId, List.of(quote.getId()))` — a `quote_id IN (?)` query plus a `Collectors.toMap` — for what is a one-row lookup, when `PolicyService.findByQuoteId(UUID, UUID)` (`policy/application/PolicyService.java:140-142`) already exists, is already used by `QuoteAcceptanceTransaction`, and does the same job with a plain equality query and no `Map` allocation. Every `GET /api/v1/quotes/{id}` for an accepted quote pays this. Low severity — correctness is unaffected — but a real, one-line-fix duplication of query paths.
- **`PolicyService.toView` re-reads the clock once per row inside `listForCustomer`'s stream** (`policy/application/PolicyService.java:238`, called from `:164` inside `.map(this::toView)`). `GET /api/v1/policies` for a customer with N policies calls `LocalDate.now(clock)` N times to derive N statuses that must all resolve to the same "today," instead of resolving it once per request. Purely theoretical impact at current scale, but a list request spanning a midnight rollover could in principle render inconsistent statuses across rows in the same response — worth resolving to today once, outside the loop.

### Aggregate views — architecture delta / altitude

- **`Policy.status(LocalDate)` (`policy/domain/Policy.java:281-289`) and `Quote.status(LocalDate)` (`quote/domain/Quote.java:260-268`) are two independently hand-written, structurally similar but not identical temporal-status derivations** — each documented in its own Javadoc as "the one place this rule is implemented," true locally, not globally. Assessed and **not treated as a defect**: the two rules genuinely differ (quote has a single boundary plus an `acceptedAt` override; policy has a two-boundary interval with no override), both are small (4–8 line) pure functions, both already carry their own dedicated unit tests, and the epic's own PR description explicitly discusses this as a considered choice ("computed on read... exactly as the quote's own rule is"). Forcing a shared abstraction over two genuinely different comparison rules would trade a marginal line-count reduction for a harder-to-read conditional — the same judgment Epic 7's retro already made for `GuestGuard`/`RoleGuard`. No action item.
- **AD-1 (policy must never import quote types) is enforced only by Javadoc/review convention, not a build rule.** Already logged as an open item in `deferred-work.md` under "Story 8.1 review (2026-09-01)," which itself notes the risk grew this story because `PolicyView` now travels into `quote.api`. Confirmed still accurate and still open; not re-logged as a new action item since it is already tracked with the same evidence — see Previous-retro follow-through below for how this maps to sprint-status.
