# Contributing — конвенции за съвместна работа

## 1. Branching модел

- `main` — винаги стабилен и работещ. Директни commit-и в `main` **не се
  правят** след старта на кода (докато проектът беше само документация,
  работихме директно в `main`).

- За всяка задача — отделен branch от `main`:

  ```text
  feature/<кратко-описание>  ->  нова функционалност
  fix/<кратко-описание>      ->  бъгфикс
  chore/<кратко-описание>    ->  конфигурация, зависимости, tooling
  docs/<кратко-описание>     ->  само документация
  ```

  Примери: `feature/quote-engine`, `feature/claim-fnol-form`,
  `fix/policy-double-issue`, `chore/setup-flyway`.

- Branch имената са с малки букви и тирета, без интервали и без issue номера
  (освен ако не ползваме issue tracker с номерация — тогава може
  `feature/12-quote-engine`).

- Тъй като нямаме строго разделение на задачите и е възможно по един и същ
  branch да работят повече от един човек едновременно, update-вай branch-а
  си от `main` с `merge`:

  ```bash
  git fetch origin
  git merge origin/main
  ```

- Force push (`--force` или `--force-with-lease`) **не се използва** в този
  проект, освен в предварително уговорени ситуации.

## 2. Commit конвенция

Следваме [Conventional Commits](https://www.conventionalcommits.org/):

```text
<тип>: <кратко описание с малка буква, без точка накрая>

[опционално тяло — какво и защо, не как]
```

### Типове

| Тип | Кога |
|---|---|
| `feat` | нова функционалност |
| `fix` | бъгфикс |
| `docs` | само документация |
| `refactor` | преструктуриране без промяна на поведение |
| `test` | добавяне/промяна на тестове |
| `chore` | конфигурация, зависимости, build tooling, CI |
| `style` | форматиране, без логика (whitespace, imports ред) |
| `perf` | оптимизация на производителност |

### Правила

- Описанието е на **английски**, повелително наклонение: `add`, не `added`
  или `adds`.
- Едно логическо изменение = един commit. Не се трупат несвързани промени
  в общ commit.
- Без commit-и от типа `wip`, `fix typo`, `asdf` в history, който отива в
  `main` — при нужда се прави `git rebase -i` за squash преди PR (виж §4).
- Ако commit-ът чупи обратна съвместимост или бизнес поведение съществено:
  `feat!: ...` + описание в тялото защо е breaking.

## 3. Pull Request процес

- Всяка задача → branch → PR към `main`. Директен push в `main` е забранен
  (branch protection се настройва в GitHub repo settings, виж §6).
- PR описанието съдържа:
  - какво прави (1–3 изречения);
  - как е тествано (unit/integration/ръчно);
  - screenshot/GIF за UI промени.
- **Минимум 1 approve** от друг член на екипа преди merge. Авторът не
  merge-ва собствен PR без review, освен за тривиални docs промени по
  договорка.
- CI (когато е налична — виж §6) трябва да е зелен преди merge.
- Merge стратегия: **Squash and merge** — историята на `main` остава по един
  чист commit на PR/задача, вместо десетки intermediate commit-и.
- След merge — branch-ът се трие (локално и remote).

---

## 4. Code review

- Ревюто гледа за: коректност на бизнес логиката, тестово покритие,
  сигурност (IDOR, валидация на вход), спазване на модулната структура
  (виж бизнес анализа — тънки controllers, бизнес логика в `application`/
  `domain`, не в React компонентите).

---

## 5. Разрешаване на конфликти

- Конфликти се решават локално, чрез `merge` на актуален `main` в
  feature branch-а (виж §1) — не чрез `rebase`, защото по branch-овете
  може да работи повече от един човек и force push би презаписал чужда
  работа:

  ```bash
  git fetch origin
  git merge origin/main
  # реши конфликтите, после:
  git add <файлове>
  git commit
  git push
  ```

- Ако двама едновременно работите по един branch — комуникирайте в чата
  преди push, за да не се получи изненадващ конфликт или загубена работа.

- При конфликт по споделени модули (`shared/`, DTO-та ползвани от
  няколко модула) — координация в чата преди merge, не "който push-не
  пръв печели".

---

## 6. Repo hygiene

- [ ] Branch protection на `main`: изисква PR + 1 approve, забранява force
      push и директен push.
- [ ] `.github/workflows/` — CI за build + тестове (Maven/Gradle backend,
      npm/vite frontend) при всеки PR.
- [ ] `.github/PULL_REQUEST_TEMPLATE.md` — чеклист какво/как е тествано.
- [ ] `CODEOWNERS` (по желание), ако искаме определени хора да ревюват
      определени модули.
- [ ] `LICENSE`, ако repo-то стане публично извън тренинг контекста.

---

## 7. Общи договорки

- Езикът в кода (имена на класове, методи, променливи, commit съобщения) —
  **английски**. Документацията в `docs/` — на български (както е сега).
- Не се merge-ва код с изключени/пропуснати тестове без коментар защо.
- Ако не си сигурен дали дадена промяна засяга друг модул — питай в чата
  преди да пушнеш, не след.
