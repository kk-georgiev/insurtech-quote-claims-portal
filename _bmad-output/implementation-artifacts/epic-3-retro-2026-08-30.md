## Findings

### Aggregate views

- **Architecture delta:** No backend files appear anywhere in the epic-3 diff. This confirms AD-8 (i18n is 100% frontend-owned) was honored end to end — the backend continues to emit only stable `code`s, never localized prose. Not a finding.
- **Duplication map:** `frontend/src/features/shells/shells.test.tsx` hardcodes the Bulgarian shell copy verbatim as an "independent oracle" (marked `APPROVED EXCEPTION` in-file), deliberately duplicating strings that also live in `bg.json`. Nothing enforces that a future edit to `bg.json`'s `shells.*` keys is mirrored here. — **Disposition: accept as-is** (already a recorded, deliberate exception; re-flagging it doesn't add information, but a translator fixing a typo in shipped copy should expect this test to need a matching update).
- **Spec-to-implementation reconciliation:** The 3.2→3.2a/3.2b split documented in `epics.md`'s blockquote (mechanical screen-copy translation vs. the architecturally risky error-messaging half) was followed exactly — 3.2a's diff touches only static JSX text and `bg.json`/`en.json` screen-copy keys; 3.2b's diff is scoped to `errorMessages.ts`, its catalog `errors.*`/`fieldErrors.*` keys, and the three forms' catch blocks. No drift between the declared split and the as-built stories. Not a finding.

### Diff-scope review (`bmad-review`: adversarial, edge-case-hunter, verification-gap)

Ran across the hand-scoped Epic 3 diff (frontend i18n + touched forms/shells). Overlapping reports from independent lenses are consolidated into one item.

- **[`LanguageToggle.tsx`, the `select` handler]** `i18n.changeLanguage(language)`'s returned promise is discarded (`void`), so a rejection (e.g. a future async-loaded resource, or an exception thrown by a `languageChanged` listener) becomes an unhandled rejection with no user-visible or logged failure — the UI could end up half-switched (storage says "en", chrome still shows "bg") with nothing to diagnose it. (adversarial + edge-case-hunter, both independently) — **Disposition: fix now.**
- **[`errorMessages.ts`, `resolveFormError`/`resolveFieldErrors` key-building]** Both functions interpolate untrusted-shaped input (`error.code`, `fieldError.field`) directly into an i18next key path (`errors.codes.${code}`, `${namespace}.fieldErrors.${field}`) with no validation. A value containing a `.` would resolve an unintended nested catalog entry instead of falling through to the generic fallback. Not currently reachable from any backend response in this codebase, but nothing enforces that invariant at the boundary where the value is trusted. (edge-case-hunter) — **Disposition: defer** (real, but currently unreachable — a guard is cheap insurance, not an urgent fix).
- **[`LoginForm.tsx`/`RegisterForm.tsx`, fieldErrors branch]** When a backend `fieldErrors` array names a field that has no corresponding rendered input (only `email`/`password` are rendered today), no error is shown anywhere — not inline, not as a form-level fallback — and the submit button re-enables silently. Not reachable today since both forms only have two fields the backend can realistically reject, but the gap has no guard if a field is added later (e.g. a confirm-password field). (edge-case-hunter, both forms independently) — **Disposition: defer.**
- **[`errorMessages.ts` / `errorMessages.test.ts`, `CODES` list]** The ten backend error codes are manually duplicated in the test file with a comment that they must be kept in sync "from the Java sources" — there is no automated check tying this list to the backend's actual code enum. Story 3.2b's own AC explicitly requires "given a new code is introduced by the backend, when it ships, then its i18n entry ships in the same change" (AD-7's naming contract), but nothing currently enforces that beyond developer discipline. (adversarial) — **Disposition: fix now** (process gap directly named by the story's own acceptance criteria — worth a lightweight contract test, not just a comment).
- **[`bg.json`/`en.json` parity test in `LanguageToggle.test.tsx`]** The "catalogs define identical key sets" test compares only the sorted list of leaf keys — it never checks that interpolation placeholders (e.g. `{{zoneId}}`) match between the two languages for the same key. A mistyped placeholder in one catalog would pass this test and then silently render the literal `{{zoneID}}` to a real user. (adversarial) — **Disposition: fix now** (small, high-value test extension).
- **[`QuoteResult.tsx`, zone-label fallback]** `t(`quote.result.zones.${zoneId}`, { defaultValue: t('quote.result.zoneFallback', {...}) })` evaluates the fallback translation eagerly on every render (nested `t()` calls are not lazy in JS), and no test exercises a `zoneId` outside the catalog's `1`–`5` range — both `QuoteForm.test.tsx` and `LanguageToggle.test.tsx`'s breakdown test only use in-catalog zone ids. (adversarial: eager-eval angle; verification-gap: untested-branch angle, both independently on the same code) — **Disposition: defer** (micro-inefficiency plus a real coverage gap, neither urgent — the fallback path exists specifically for zones the backend might add before the catalog catches up).
- **[`RegisterForm.test.tsx`, `QuoteForm.test.tsx`]** `LoginForm.tsx` holds errors unresolved in state and resolves them at render time specifically so a visible error re-translates on a language switch with no resubmit — and `LoginForm.test.tsx` has two dedicated regression tests guarding exactly that contract. `RegisterForm.tsx` and `QuoteForm.tsx` implement the identical render-time-resolution pattern but have no equivalent regression test in either file. (verification-gap) — **Disposition: fix now** (cheap to add, closes a real blind spot on a pattern this project has already regressed on once, per `LoginForm.test.tsx`'s own comments).
- **[`shells.test.tsx`, cross-contamination check]** Role-name cross-contamination is checked with a plain substring match (`text.toLowerCase().includes(stem)`) on un-inflected Bulgarian stems, so an unrelated future word containing the stem (e.g. "агенция" contains "агент") would fail this test for the wrong reason. (adversarial) — **Disposition: accept as-is** (real but low-probability; flagging it here is enough to save investigation time if it ever fires).
- **[English catalog quoting]** `en.json`'s region-code example strings use Bulgarian/German-style low/high guillemets (`„CA“`) rather than standard English double quotes. (adversarial) — **Disposition: fix now** (trivial, visible polish nit in the just-shipped English locale).
- **[`HealthStatus.tsx`]** The health-check failure reason moved from on-screen text to `console.error` (per AD-7 — backend-facing diagnostics don't belong in user-facing UI), but no test asserts `console.error` is actually called on either failure branch. (adversarial) — **Disposition: defer** (the one place this diagnostic now lives has no regression guard, but it's not user-facing behavior).
- Minor/no-action items noted for completeness: a few stray double-blank-lines left by removed helper functions across three call sites (cosmetic, would be caught by a lint pass) and a `FormFailure` type that can't distinguish "malformed token" from "no error object" (low-risk type-precision nit) — both **rejected** as too trivial for a tracked action item.

### Behavior verification

Exercised live against the currently-running dev stack (native backend on `:8080`, native frontend on `:5173`, containerized Postgres) — not merely re-asserted from tests:

- First load renders in Bulgarian by default (`Портал за автозастраховане — оферти и щети`, `Вход в профила`).
- Submitting login with an unknown email/wrong password returns the translated generic error `Грешен имейл или парола.` (Story 1.3's no-user-enumeration contract preserved).
- Toggling to English switches the header, nav, and the *already-displayed* error message to `Incorrect email or password.` instantly, with no reload and no re-submission — confirms the render-time-resolution contract Story 3.2b's AC and `LoginForm.test.tsx`'s regression tests describe.
- On the Register screen, submitting an invalid email and a 1-character password produces translated field-level validation errors in English (`Enter a valid email address (up to 255 characters).`, `The password must be between 8 and 100 characters.`) — confirms field-level errors are the frontend catalog's translated text, never Bean Validation's raw English.

Not exercised live in this retro (would require driving the full quote flow and a staff login, out of proportion for a single retro session): the quote-breakdown zone label rendering in Bulgarian, and the three staff shells' translated copy. Both are covered by the existing automated test suite (`LanguageToggle.test.tsx`, `shells.test.tsx`), which passed as part of the diff-scope review's evidence gathering.

## Action items

1. **Handle `i18n.changeLanguage`'s rejection in `LanguageToggle.tsx`** — attach a `.catch()` (log via `console.error`, matching the AD-7 diagnostics convention `HealthStatus.tsx` already established) instead of discarding the promise with `void`. *(fix now; remediation)*
2. **Add a contract check tying `errorMessages.ts`'s `CODES` list to the backend's actual error-code enum** — even a lightweight script/test that parses the backend's error-code source and asserts it's a subset of the frontend catalog's `errors.codes` keys, directly enforcing Story 3.2b's own AC ("a new code ships with its i18n entry in the same change"). *(fix now; remediation + process lesson: a story's own AC named this contract but shipped it as a comment, not an enforced check — worth catching in review before merge next time a new error code is added.)*
3. **Extend the bg/en catalog-parity test to assert interpolation placeholders match**, not just key sets, in `LanguageToggle.test.tsx`. *(fix now; remediation)*
4. **Add render-time-resolution regression tests to `RegisterForm.test.tsx` and `QuoteForm.test.tsx`**, mirroring `LoginForm.test.tsx`'s two dedicated tests for "error re-translates on language switch without a resubmit" — closing a blind spot on a pattern this project has already had to guard against once. *(fix now; remediation)*
5. **Fix non-native guillemet quotes (`„CA“`) in `en.json`'s region-code example strings** to standard English double quotes. *(fix now; remediation — trivial)*
6. **Guard `errorMessages.ts`'s key interpolation against field/code names containing `.`** before they're used to build an i18next key path, so an unexpected value falls through to the generic message instead of silently resolving an unrelated nested catalog entry. *(defer; not currently reachable from any backend response, but cheap insurance at the trust boundary.)*
7. **Give `LoginForm`/`RegisterForm` a form-level fallback when a backend `fieldErrors` entry names a field with no rendered input** (currently only `email`/`password` exist), so a future field addition doesn't silently produce zero visible feedback. *(defer; not reachable today, but has no guard for when a field is added.)*
8. **Add a test for `QuoteResult`'s `zoneFallback` branch** (a `zoneId` outside the catalog's `1`–`5` range) and reconsider making the fallback translation lookup lazy instead of always-evaluated. *(defer; remediation, low urgency.)*
9. **Add a `console.error`-call assertion to `HealthStatus`'s failure-path tests**, closing the one place this diagnostic now lives without a regression guard. *(defer; remediation, low urgency.)*
10. **Escalate `epic-2-retro-item-14`** (LoginForm token/role de-duplication) — Story 3.2b already touched `LoginForm.tsx`'s surrounding code for an unrelated reason without fixing this; worth doing the next time this file is opened rather than deferring indefinitely. *(process lesson: a story touching a file with a known open action item is a good trigger to fold that item in, rather than editing around it again.)*

Items 1–10 are proposed for the normal dev backlog; none were applied directly in this retrospective (all are either genuine hardening/test-coverage work, or process items — no fix was small and unambiguous enough to apply without a human decision on scope, unlike Epic 4's four one-line doc corrections).
