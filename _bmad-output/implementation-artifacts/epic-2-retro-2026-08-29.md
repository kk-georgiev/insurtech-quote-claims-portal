## Findings

### Aggregate views

- **[roleHome.ts:9,51-59 / LoginForm.tsx:84-89] Duplication — token-decode-and-role-validate logic exists in two independent places.** `getCurrentRole()` (added Story 2.4) and `LoginForm`'s inline `decodeToken` → `isRole` sequence (Story 2.2) do the identical check against two different token sources. Story 2.4 never revisited `LoginForm.tsx` to reuse its own new helper. — **Disposition: fix now.**
- **[roleHome.ts:14-19 vs. router.tsx:28-44] `STAFF_ROLES`/`StaffRole`, exported from production code by Story 2.4 specifically so the guard wiring could derive from a single staff-role source, are consumed only by tests — `router.tsx`'s 4 `<RoleGuard role="...">` blocks remain hand-enumerated with no link back to `ROLES`/`STAFF_ROLES`.** A 5th role would compile-fail `ROLE_HOME` but silently ship with no matching guard. — **Disposition: defer** (architecture hardening; the milestone's role set is fixed, so not urgent — revisit if a role is ever added).
- **[SeededStaffAccountsTest.java, shells.test.tsx, router.test.tsx, LoginForm.test.tsx] God-class / size growth — none found.** Ranked the top 5 files by net epic-2 churn and read each; every one is cohesive (one migration's guarantees, one placeholder-screen contract, one route table's two concerns). Not a finding.
- **[LoginForm.tsx:85-88 vs. RoleGuard.tsx:26-27] Pattern divergence — an unusable role claim gets two different UX treatments** depending on which story's code path hits it: a visible generic error with an editable form at login time, vs. a silent redirect to `/login` via the guard for the same underlying condition reached by direct navigation. Not called out as intentional anywhere. — **Disposition: accept-as-is for now** (natural byproduct of two stories solving adjacent-but-different moments; worth a deliberate UX decision later, not blocking).
- **[epic-2-context.md:23 vs. :44] Spec-to-implementation reconciliation — the epic's own compiled context still contradicts itself**: line 44 (UX narrative) promises staff see "a role-specific navigation menu"; line 23 (constraint) says "no sub-navigation inside a role." Story 2.3's spec (`spec-2-3-*.md:28,112`) correctly resolved this as "no menu" and the code matches that resolution — but `epic-2-context.md` itself was never corrected, so re-reading it alone still gives a wrong picture of what shipped. — **Disposition: fix now** (trivial doc correction).
- **[epic-2-context.md:40 vs. diff] `react-i18next` pinned, unused — not a gap.** Consistent with the epic's own stated deferral to Epic 3 (line 27, line 53). Recorded so it is not re-flagged later.

### Cross-story boundary review (adversarial + edge-case lenses)

- **[shells/{agent,liquidator,administrator}/*Shell.tsx, shells.test.tsx] Stale doc comments left behind by Story 2.4.** All three staff shells, plus a `shells.test.tsx` inline comment, still say "there is no route guard until Story 2.4, so an anonymous visitor can reach this URL" — now false. Nobody revisited Story 2.2/2.3's own comments when 2.4 shipped. — **Disposition: fix now** (doc-only).
- **[api/authToken.ts, `decodeToken` doc comment] Now-inaccurate comment.** Still says the decode is "only for display purposes," unchanged since Story 1.3, despite Story 2.2 (`LoginForm`) and Story 2.4 (`RoleGuard`) both now using its output to drive real navigation/access-gating decisions. — **Disposition: fix now** (doc-only, bundle with the item above).
- **[router.tsx / LoginForm.tsx / RegisterForm.tsx] `RoleGuard` covers the four shell routes but not `/login`/`/register` against an already-authenticated visitor.** Confirmed live (see Behavior verification): a logged-in AGENT navigating to `/login` sees the login form again instead of being redirected to `/agent`. This also means an authenticated user can silently swap identity by logging in again as a different role while a guarded route may still be mounted — no test anywhere in the epic covers this path. — **Disposition: fix now.**
- **[RootLayout.tsx:17-21] Nav was never made role/auth-aware by any of the 4 stories**, despite Epic 1's own retro predicting this exact follow-up ("No logout capability anywhere... Natural follow-up once Epic 2's role-based routing/nav lands"). A staff user on their guarded, non-interactive placeholder screen has zero in-app way back anywhere — no logout, no link to their own shell reasserted, nav still shows plain "Register"/"Login" as if anonymous. — **Disposition: defer as a proposed story** (out of any single story's declared scope; sizeable enough to spec properly rather than patch in).
- **[router.test.tsx / shells.test.tsx] Test duplication** — the `RoleGuard` describe block and `shells.test.tsx`'s flipped anonymous-visit case both cover the same 3 staff-role anonymous-redirect scenarios via two full-route-tree renders. **[LoginForm.test.tsx:27-30]** hand-rolls the identical fake-JWT-encoding logic that Story 2.4 extracted into `frontend/src/test/seedToken.ts` for the other two files, but never backported here. — **Disposition: defer** (test-quality cleanup, low risk).

### Verification-gap review

- **[JwtService.java:55, roleHome.ts:14-15,58-66, LoginForm.tsx:84-98, RoleGuard.tsx:23-28] No test anywhere ties the backend JWT `role` claim's actual wire format to the frontend's `isRole`/`getCurrentRole` validation.** Backend's `SeededStaffAccountsTest` compares against the Java `Role` enum, never the raw claim string; every frontend test fabricates its own `'AGENT'`/`'LIQUIDATOR'`/etc. strings rather than decoding a token that actually came from `JwtService`. If the claim's format ever drifted (e.g. a `ROLE_` prefix, a common Spring Security idiom), both CI suites would stay green while every real login in production silently failed to route (generic error, form stays editable) — the epic's headline claim would be completely broken with no automated signal. **Empirically re-checked live against the real stack** (see Behavior verification) — the contract holds correctly today; this is a regression-prevention gap, not a currently-failing behavior. — **Disposition: fix now** (add a contract/integration test; no e2e framework exists in the repo yet, so this is scoped as new test infrastructure, not a one-line patch).
- **[router.test.tsx / RegisterForm.test.tsx] `/register` is never rendered through the real route table** — `RegisterForm.test.tsx` mounts the component standalone. Already recorded in Story 2.4's own deferred-work entry; re-confirmed true, not a new finding. — **Disposition: already tracked, no new action.**

## Acceptance verdict

**accepted-with-open-items** (criteria: **declared** — each of the 4 stories carries explicit Given/When/Then ACs in `epics.md`).

All declared ACs are met by direct evidence:
- 2.1: seeded accounts exist, hashed, log in successfully — confirmed by `SeededStaffAccountsTest` and this retro's live login test for all 3 staff roles.

No blocking finding contradicts a declared AC. The findings above are real (most notably the `/login` re-authentication gap, confirmed reproducible live, and the role-claim contract verification gap) but sit adjacent to, not in violation of, what the epic committed to — hence open items, not rejection.
